# 顶点排列与位置块重叠共享

本轮交付 `delivery/POPY_VTS_Overlap.zip`，基线为 `POPY_VTS_Exact2`。继续保留上一性能版的画面，不新增拟合误差、减面、参数裁减或贴图缩小。本轮的可靠收益是文件和少量内存，**没有测到可信的帧率提升**。

## 字节级的“借用存储”

MOC 的关键形引用一段连续位置数组。普通去重只能发现完整数组相同，无法发现两个网格仅共享部分顶点轨迹。

本轮将每个顶点的全部主关键形、非中性 BlendShape 值组成完整 float32 位模式轨迹；参数轴、关键值、父级和 BlendShape 程序不同的对象不相互匹配。比较原始 `uint32` 位模式，正负零也区分。对同一程序组做带权、不相交的网格配对，将共同轨迹排列为 A 的后缀和 B 的前缀。144 个隐藏来源网格改了顶点顺序，位置和 UV 同步排列、索引反向映射；默认交付**没有改变任何三角形的语义顺序或绕向**。

导出后，通过未修改运行时公开 API 获取每个主/BlendShape 行的真实归属和长度。在真实 MOC 字节上再次比较公共尾部/头部，完全相等才连边。以共享字节数作为权重，用禁止环、入度/出度均不超过一的贪心路径覆盖构造不可变位置池：

```
A = [A 私有区 | 公共轨迹]
B =           [公共轨迹 | B 私有区]
池 = [A 私有区 | 公共轨迹 | B 私有区]
```

A/B 的引用指向同一池的两个连续区段。每个读取字节保持原值，没有追加数学计算、恢复回调或运行时解压，仍然 **0 Glue**。所有引用按二维 float32 坐标对对齐；未知布局、Warp 池、范围冲突和未覆盖的位置行被拒绝。原有颜色/整块位置去重继续使用。

共 3,657 对关键形字节重叠核对成功，无不匹配；加上通用首尾包含，共建立 3,967 条存储路径边，位置池约 82.06→77.27 MB。全模型 MOC 88,302,400→83,511,744 字节（约 −5.4%）。ArtMesh 2,641、顶点 170,693、三角形 149,318、主关键形 108,270、2 个变形器均保留。

## 质量与边界

1,803 姿态，307,759,479 次原顶点比较按排列逆映射核对，位模式零差异；UV 按原顶点逐位一致。362 个全分辨率 RGBA 渲染逐像素一致，运行时资源字节摘要相同。80 个遮罩上下文、牙齿修复、39 参数、58 动作、24 表情及原贴图保留。每个顶点执行的浮点插值程序不改变，因此不是以减少采样或舍入换体积。

ArtMesh ID 保留；内部顶点编号改变，用户的逐顶点附着设置可能需要重建。前一有损拟合版本既有的复合动作误差没有在本轮修复。目标 Cubism 5.0/MOC v5 不变，没有新 CMO3，也未做 VTube Studio、官方 Core 或 Editor 实机验收。

## 本机测量

| 指标 | Exact2 | 重叠存储版 |
|---|---:|---:|
| MOC 字节 | 88,302,400 | 83,511,744 |
| CPU Driver 中位数 | 2.056 ms | 2.062 ms |
| 参数设置至 GPU 完成中位数 | 31.143 ms | 31.003 ms |
| 同指标 P95 | 33.434 ms | 33.464 ms |
| 重复单进程峰值 RSS 中位数 | 453.84 MiB | 448.27 MiB |

RTX 5080 Laptop GPU、原生 DX12、未修改 Ayagami `0d1d7aa3efe57b1b363b72e672e353c52a9c15d6`。CPU/GPU 同一 60 姿态交替执行 4 轮，各 240 个样本，每模型预热 5 帧。GPU 包含提交/同步，不含图像下载写盘。均值/中位/P95 变化不支持可靠的速度提升结论。

内存以 ABBA BAAB 运行 8 个独立单模型进程，各 65 姿态、不下载或写 PNG，加载/预热也计入峰值。基线 452.59–458.99 MiB，候选 447.76–454.13 MiB，中位数约下降 1.2%；范围有重叠，幅度较小。单次图片回归 657.63→525.91 MiB 受瞬时分配影响，不用作稳定内存收益。所有数字都是本机原生 Ayagami 结果，非 VTS 的 FPS/内存。

## 两个没有作为默认交付的候选

**共享轨迹载体 + 恒定 Glue**：`trajectory_pool.py` 将 123,550 个隐藏来源顶点集中为 103,537 条唯一轨迹，17 个隐藏载体、174 个恒定 Glue 拷贝，MOC 81,801,472 字节。1,803 姿态顶点逐位相同、362 RGBA 相同；透明度恒零的来源颜色/深度不参与 RGB 或遮罩 alpha，可与原不可观察值不同。但同一配对测试 CPU 中位 2.070→2.601 ms，完整帧中位 30.731→31.228 ms，**因此拒绝替换性能版**。它是独立研究候选，不在交付包中。`world_zero` 适配及追加新零坐标块只用于该候选，不修改原有共享块，GPL 导出边界不变。

**三角/顶点缓存布局**：参考 [Forsyth 原始算法说明](https://tomforsyth1000.github.io/papers/fast_vert_cache_opt.html) 的 LRU/valence 打分思路，以优先队列实现；顶点 first-use 布局思路亦见 [meshoptimizer 官方说明](https://github.com/zeux/meshoptimizer#vertex-fetch-optimization)。没有引入库二进制或复制其实现。仅全不透明贴图、恒零主画面透明度、没有自身遮罩的隐藏来源可改变三角顺序；Native 检查器直接核对所有 alpha 字节和原始有向三角形排列。候选仍通过全部几何/像素检查，但完整帧中位 30.714→30.684 ms、P95 35.410→35.979 ms，没有可靠改善，故默认选用三角顺序也不变的存储配置。

这些候选的数值保留在 `benchmarks/popy/fullbody/trajectory_pool_trial.json` 和 `cache_layout_trial.json`。不把它们的体积或顶点复用率当作性能提升。剩余成本主要是遮罩和大量网格的逐帧准备/提交。

## 复现

需要本机 Exact2、对应冻结 IR、回归用例、固定依赖与已构建的独立 GPL 导出器；角色资产不随仓库分发：

```powershell
cargo build --release --locked --manifest-path rust/Cargo.toml -p popy-validate --bins
python -m popy.cache_review all --storage-only
```

阶段为 `build|export|validate|memory|report|package`。打包要求模型/资源/映射/用例摘要匹配验证输入、362 RGBA 零差异，并包含重复内存数据。去掉 `--storage-only` 可重复缓存候选；共享载体候选用 `python -m popy.trajectory_pool build` / `export` 单独生成，不会覆盖默认包。

安装到 `VTube Studio_Data/StreamingAssets/Live2DModels/`，入口 `POPY.model3.json`，仍需 256 masks、每组至少 512×512。旧包保留可回退。
